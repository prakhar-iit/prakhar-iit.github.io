Production · Java

Agent framework for production investigations

A multi-agent framework I architected and built in Java that lets LLM agents investigate production issues the way an on-call engineer would: plan, gather evidence from logs, code, tickets and databases, and report a root cause.

The problem

Debugging a data intelligence platform means piecing together evidence from many places: service logs, databases, tickets, code and team runbooks. It's slow, it repeats, and much of it follows known procedures. The goal was an agent system that can do this safely on live infrastructure, inside the existing service's security and audit setup.

How it works

  • Three agent levels. A lightweight router answers simple questions directly or fires tools in parallel. Harder questions go to a planner that runs a prebuilt workflow (root-cause analysis, issue triage, log analysis), which hands deep digging to a triage agent that loops over logs, code and diagnostic queries. Most questions are answered cheaply at the first level.
  • Durable runs. Each investigation is a checkpointed background job, saved after every step. It survives a server crash and picks up where it left off, so long autonomous investigations can run unattended.
  • Tool lookup instead of sending every tool. The catalog of diagnostic actions is large and growing. Hybrid semantic + keyword search on Oracle Database vector search gives the model only the few tools that fit each step, keeping long loops within the context budget as the catalog grows.
  • A structured scratchpad. The triage agent keeps typed working notes (facts, evidence, event timeline, next actions) and passes only its conclusions back to the planner, not the full transcript.
  • Skills and runbooks as searchable memory. Operating procedures are stored as reusable skills that the planner retrieves and assembles into plans, and that engineers can query directly for how-to answers.
  • Safe and inspectable. Read-only by design. Every step, tool call and output is saved and shown in the UI, so engineers can see exactly how the agent reached its answer.

Built on it

An autonomous multi-agent root-cause analysis system for on-call engineers, a natural-language interface for querying tickets, data and docs, and a scheduled monitor that scans service logs and routes exceptions to the owning team.

Customer-facing · LangChain

Action agents with human-in-the-loop approval

Domain-specific agents that help customers find information, troubleshoot their own issues and carry out multi-step actions, with a person signing off on actions.

The problem

Customers want an agent that can actually do things in their environment, not just answer questions. Taking real actions on a customer's behalf needs tight control over which tools it can use, how much it loads into context, and when a person has to approve.

How it works

  • A custom agent harness on LangChain for domain-specific agents that reason through multi-step workflows to answer, troubleshoot and act.
  • A tool gateway that discovers and runs tools (APIs and SQL) across cloud services, microservices and databases, so agents work through one controlled layer instead of separate integrations.
  • Two levels of knowledge. Core domain knowledge is always loaded; deeper knowledge and skills load only when a task needs them, keeping context small.
  • Human-in-the-loop approval. A policy sends agent actions to a person for approval, so customers can hand off real operations without losing oversight.
  • A card-based agent interface. Agent output appears as structured cards instead of plain chat.

Retrieval Stack Study

Benchmarked six retrieval methods — BM25, Word2Vec, sentence-transformers, Matryoshka embeddings, hybrid fusion and cross-encoder reranking — on 20K arXiv abstracts with a 400-query eval set.

  • 0.9885 nDCG@10 for hybrid fusion, best of all methods
  • 8.5% vs 12.4% loss truncating 768→64 dims (MRL vs control)
  • N1.3 lexical vs N0.95 vector search cost scaling
